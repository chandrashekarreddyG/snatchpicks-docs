Hosting options & cost

Run it in Mumbai

SnatchPicks' users are in India, but its servers run in US East. This page compares the realistic ways to host it close to Indian users, for a team of one or two people. It covers latency, ops effort, migration effort and monthly cost at three stages: v0 (~1k daily users), v0.2 (~10k) and v1 (~100k).

1Summary

The four facts that drive the recommendation.

🏆

Recommended: stack B Recommended

Vercel Pro in Mumbai (bom1) + Supabase Postgres Mumbai + Upstash Redis Mumbai. About $45/mo at v0, $81/mo at v0.2 and $733/mo at v1, before the shared add-on services.

⚡

1.7 s → ~155 ms

The homepage took 1.7 s to first byte, measured cold, today. Uncached pages on stack B are estimated at about 155 ms. Cached anonymous pages would load in about 20–60 ms from Indian edge locations.

💼

Vercel Pro is required

Vercel's Hobby plan is for non-commercial use only, and its fair-use guidelines list “Affiliate linking is the primary purpose of the site” as commercial. SnatchPicks earns affiliate revenue, so it needs Pro.

🗺️

Neon has no India region

The current database provider's nearest region is Singapore, and a project's region can't be changed. Running functions in Mumbai against a Singapore database is the slowest option of all.

The commercial-use rule, quoted “Hobby teams are restricted to non-commercial personal use only. All commercial usage of the platform requires either a Pro or Enterprise plan.” The examples include “Affiliate linking is the primary purpose of the site.” Source: Vercel fair-use guidelines (read 2026-11-11). Hobby also rejects any deployment whose cron jobs run more than once a day, and SnatchPicks has jobs every 15 and 30 minutes.

2Why the region matters

A page that misses the cache waits for the trip to the function, then for every database round trip one after another. A page makes several sequential queries, so the distance between the function and the database counts several times.

The model (estimates)

TTFB (uncached) ≈ RTT(shopper → edge) + RTT(edge → function) + k × RTT(function → database) + render time

InputAssumed value
Shopper → Indian edge location5–25 ms
Indian edge → Mumbai function5–30 ms
India → Singapore50–70 ms
Mumbai ↔ Singapore (function to database)50–60 ms
India → US East190–250 ms
Sequential database round trips per page (k)about 4
Render time80–150 ms

Worked out: A1 ≈ 15 + 60 + 4×1 + 120 ≈ 200 ms. A2 ≈ 15 + 15 + 4×55 + 120 ≈ 370 ms. B ≈ 15 + 15 + 4×1 + 120 ≈ 155 ms. These are typical published round-trip times, not measurements. Measure with a probe in India before and after any move.

4Candidate stacks

Nine stacks, each realistic for one or two people. Latency is the estimated uncached time to first byte from India. Migration effort is S (days), M (one to two weeks) or L (several weeks).

🟧

A1 · Vercel Singapore + Neon Singapore

Components: functions in sin1, Neon in Singapore, Upstash. Latency: ~200 ms. Ops: lowest. Migration: S (set the region; move Neon to Singapore if it isn't there already). Lock-in: low–medium. Risks: every uncached request pays 50–70 ms to reach Singapore; data isn't stored in India. Keeps Neon's free database branch per preview.

⛔

A2 · Vercel Mumbai + Neon Singapore Avoid

Components: functions in bom1, Neon in Singapore. Latency: ~370 ms, the worst option, because every sequential query crosses Mumbai↔Singapore. Ops: lowest. Migration: S. Lock-in: low–medium. Risks: the delay compounds with the number of queries per page; scheduled ingestion runs far from the database.

🏆

B · Vercel Mumbai + Supabase Mumbai + Upstash Mumbai Recommended

Components: functions in bom1, Supabase Pro Postgres (with its connection pooler), Upstash Redis, all in Mumbai. Latency: ~155 ms, the best of the managed options. Ops: low. Migration: S–M (dump and restore Postgres, then swap the pooled and direct database URLs). Lock-in: low; Supabase is plain Postgres. Risks: loses Neon's free branch per preview (Supabase branches are paid); the pooler settings must be right; the US-hosted scraper is slow against a Mumbai database until its writes are batched.

🟨

C · AWS Mumbai: ECS (Fargate) + RDS + Upstash

Components: container on ECS Express Mode with Fargate ARM tasks, a load balancer, RDS Postgres, Upstash, EventBridge Scheduler, a CDN in front. Latency: ~130–200 ms. Ops: medium–high (networking, IAM, certificates, patching, alarms, home-made previews). Migration: L. Lock-in: medium. Risks: App Runner is closed to new customers, so ECS is the managed container route; egress costs $0.1093/GB without a free CDN in front; the load balancer is a fixed cost.

🟫

C′ · AWS Amplify + RDS Mumbai

Components: Amplify Hosting (official Next.js 12–15 support, built-in image optimization) + RDS. Latency: ~130–200 ms. Ops: medium. Migration: M. Lock-in: medium. Risks: $0.15 per GB served makes it the most expensive option at v1 (~$722 a month for bandwidth alone).

🟦

D · Google Cloud Mumbai: Cloud Run + Cloud SQL

Components: Cloud Run (one warm minimum instance), Cloud SQL Postgres, Upstash, Cloud Scheduler, Cloud Run Jobs, a CDN in front. Latency: ~130–200 ms warm; a cold start adds 1–3 s (estimate). Ops: medium. Migration: M–L. Lock-in: medium. Risks: Cloud SQL's Mumbai prices are unverified; no built-in connection pooler on the standard edition (verify).

🔷

E · DigitalOcean Bangalore

Components: App Platform containers, managed Postgres (with built-in pooling), Upstash or managed Valkey, a CDN in front. Latency: ~150–220 ms. Ops: low–medium. Migration: M. Lock-in: low. Risks: availability in BLR1 must be verified; shared containers don't autoscale; a high-availability standby costs extra.

🟠

F · Cloudflare Workers + Hyperdrive → Supabase Mumbai Reassess at v1

Components: Next.js on Workers via the OpenNext adapter, Hyperdrive connection pooling into the Mumbai database, Cloudflare Images, cron triggers, Queues. Latency: ~150–250 ms; compute runs at Indian edge locations. Ops: medium. Migration: M–L. Lock-in: medium–high. Risks: a community adapter (supports the latest Next.js 15 minors, not Node middleware); the database client needs a driver adapter; the 10 MiB compressed Worker size limit; no egress charges.

🖥️

G · India VPS + Docker + Coolify

Components: a Linode Mumbai, DigitalOcean Bangalore or E2E server running the app, Postgres and Valkey in containers under Coolify, with a CDN in front; a managed database by v1. Latency: ~130–220 ms. Ops: high (patching, backups, monitoring, a single server until v1). Migration: M. Lock-in: lowest. Risks: one maintainer owns uptime and data durability.

Dropped from the shortlist Fly.io has no India region (Singapore is nearest, and outbound traffic to India costs $0.12/GB). Render and Railway reach Asia only through Singapore (not verified), so they were not costed.

6Cost

All usage numbers are estimates from the model below. Prices were read on 2026-11-11 (see Sources). Re-run the formulas when traffic or prices change.

Usage model: key assumptions

  • Web share of daily users: 100% at v0, 70% at v0.2, 50% at v1 (the app ships in v0.2). 1.3 sessions per user per day; 4, 4.5 and 5 pages per session.
  • Bots and crawlers add 30% on top of human page views. 1.5 API calls per page view; 8 (v0.2) or 10 (v1) per app session.
  • 8 CDN requests per page view, 6 of them images. HTML 60 KB, API 8 KB, static files about 150 KB and images 25 KB each.
  • Cache hit ratio: 0% before the caching change (C16), because the header makes every page dynamic. After it: 85% of anonymous HTML and 60% of anonymous API reads. Signed-in traffic (20–30%) is never cached. v0 is modelled before C16; v0.2 and v1 after it.
  • CPU per dynamic request: HTML 60 ms before and 40 ms after; API 15 ms; middleware 2 ms.

Sensitivities

  • Before the caching change, Vercel alone on stack B costs about $716/mo at v1 instead of about $516.
  • Leaving the middleware to run on every page adds about $27/mo at v1. A second Vercel seat adds $20/mo.
  • Without the Flat Rate CDN, v1 CDN and bandwidth on Vercel would be about $1,016/mo instead of $300. Turn it on.
  • Vercel's platform cost by daily users, in Mumbai, after caching: 10k → $34, 20k → $91, 30k → $169 (the $100 tier), 40k → $391 (more than 50M CDN requests forces the $300 tier), 60k → $434, 100k → $520.
  • Images are 6 of the 8 static requests per page view. Serving them from a separate image service delays the CDN tier jump.

8Migration path to stack B

A database move plus a region setting. The application code doesn't change.

Do this week

  1. Confirm the Vercel team is on Pro. Hobby breaks the terms for an affiliate site and rejects the sub-daily cron jobs.
  2. Check which Vercel config file is read. Look at the project's root directory setting and the Crons tab, and confirm all 8 jobs are registered. Put the region and cron settings in the file Vercel actually uses.
  3. Read the current Neon region from the database host name (the part before .aws.neon.tech).
  4. Record the region decision: Vercel Mumbai with a Mumbai Postgres provider.
  5. Create Supabase Pro and Upstash Redis in Mumbai. Rehearse the dump, restore and migrations, with a small connection limit on the pooled URL.
  6. Cut over: write freeze, dump and restore, swap the pooled and direct database URLs in Vercel and CI, set the region to Mumbai, then measure from India (baseline 1.7 s).
  7. Narrow the middleware to the paths that need it. Today every page view is a billed middleware run.
  8. Security hardening (tracked privately).
  9. Turn on the Flat Rate CDN and set spend alerts and limits on Vercel, Supabase and Upstash.
  10. Point snatchpicks.com at Vercel, and add a health check with an uptime monitor probing from India.

Checks after the cutover

  • Vercel's response headers show the Mumbai region (bom1).
  • TTFB p50 and p95 from India, compared with the 1.7 s baseline and the ~155 ms estimate.
  • The database pooler's connection count during the 15-minute cron job.
  • Vercel's usage dashboard compared with the estimates above: CDN requests, origin transfer, function runs and image transformations.
  • How long a scraper run takes from GitHub Actions against the Mumbai database, until ingestion moves to Mumbai cron jobs.

GST

Online services bought from foreign providers (Vercel, Supabase, Upstash, Resend, Sentry, Expo) count as OIDAR. A GST-registered business pays 18% under reverse charge and can usually claim it back as input tax credit (ITC). Otherwise the provider charges the 18%. Indian invoices (for example AWS India, Google Cloud India, E2E) add 18%; Indian list prices exclude it.

🔐

DPDP Act 2023

Section 16 allows personal data to go abroad except to countries the government restricts (a negative list). The Act doesn't require general consumer data to stay in India; sector rules can (for example RBI rules for payment data). The DPDP Rules 2025 were notified in November 2025, and the cross-border and significant-data-fiduciary rules are reported to start on 13 May 2027. An India database region still helps latency and user trust.
