How SnatchPicks works today

A factual tour of what is in the code right now: what shoppers can do, how deals get in, how they are ranked and delivered, and the platform underneath. Gaps are marked as gaps.

Now built and running Gap known bug or missing piece Planned designed, not built

1Product & surfaces

One web app is the primary destination, where every link lands and where SEO lives. The native app and extension are thin clients over the same API.

🌐

Web app (primary) Live

Next.js site and API on Vercel. Feeds, deal pages, search, store and category pages, alerts, saved deals, profile and the admin console.

📲

Native app Not in stores

Expo app for iOS & Android: a thin client over the same API. Deals feed, search, alerts, profile, and deal detail with comments and a price sparkline.

🧩

Browser extension Unpublished

Chrome (MV3). On a product page at a supported store it shows the SnatchPicks deal, price history and cashback; at checkout it offers coupons to try.

✈️

Telegram

Deals are auto-posted to the SnatchPicks channel when their hot score first reaches 10, and when an admin approves a qualifying scraped deal. A bot answers browsing commands.

📸

Instagram

A discovery channel, posted by hand today. There is no automation in the code yet.

✉️

Email & push

Alert emails, daily and weekly digests, “expiring soon” and “just went LOOT” pushes for saved deals, and price-drop alerts.

4The core flow

Deals come in, get checked, get ranked by the community, and get pushed to the people who want them. Every click out feeds the affiliate model that funds the loop.

Follow one deal, from spotted to sold

Press play, or click any stop, to watch an example deal move through SnatchPicks. The deal card changes as each part of the system acts on it.

This walkthrough shows the designed flow. Two steps don't work like this yet: the duplicate check currently matches a new submission against itself, so ordinary submissions are auto-rejected as duplicates; and app push is not configured, so alerts reach shoppers by email only. Both are listed under Known limitations.

Three typical journeys

🛍️ The shopper

  1. Opens the Hot feed, or gets an alert.
  2. Opens a deal: sees the real price, original price, coupon and price history.
  3. Saves it, votes, or clicks out to buy.
  4. Gets nudged if a saved deal is about to expire.

✍️ The contributor

  1. Signs in and submits a deal (up to 3 per hour).
  2. Automated checks approve, reject or queue it within seconds.
  3. Upvotes raise the deal's rank and the poster's reputation.
  4. At milestones (5, 10, 25, 50, 100 and 500 upvotes) they get an in-app notification.

🧑‍⚖️ The admin

  1. Reviews submissions the automated checks weren't sure about.
  2. Reviews scraped deals, picks a category, approves or rejects.
  3. Handles reports, features deals, sets the deal of the day.
  4. Watches analytics and scraper runs.

5Deal ingestion today

Deals enter through two doors: user submissions, which go through an automated moderation pipeline, and the scraper, whose items always wait for a human. Both end up as the same Deal record in the public feed.

No real automated supply yet. The scraper's schedule has been paused since 14 June 2026, and no partner-feed key has ever been configured, so every adapter skips. In practice the feed is filled by hand-curated and user-submitted deals.

Door 1: user submission and the moderation pipeline

CheckRuleOn failure
1 · URL safetyGoogle Safe Browsing: malware, phishing, unwanted software.Auto-reject
2 · DuplicateSame store URL (ignoring common tracking parameters) already ACTIVE, PENDING or FRONTPAGE. Bug The new deal is already saved as PENDING when this runs, and the check doesn't exclude it, so it matches itself.Auto-reject
3 · Price sanityNegative price · deal price above original · discount over 99% · original more than 5× the price on items under ₹10,000 (MRP inflation) · over 90% off on items under ₹50,000.Human review
4 · AI checkgpt-4o-mini classifies title, description and URL as legit / spam / malicious / unclear with a confidence score. It auto-decides only at ≥ 0.82.Reject, or human review if unsure

The fake-MRP rules run only on this door. Deals created by the scraper or by an admin skip them.

Door 2: the scraper

The scraper (packages/scraper) is a Node script run by a GitHub Actions workflow. It has five adapters; each returns nothing until its partner key is configured.

AdapterSourceFilter sent to the sourceCap per run
amazonKeepa deals API (Amazon.in)Price drops of 20% or more50
flipkartFlipkart Affiliate API, “best offers” feedAll categories80
myntraMyntra affiliate JSON feedFixed fashion feed80
cuelinksCuelinks Offers API (many merchants)None100
inrdealsINRDeals Deal Feed API (many merchants)None100

How a run works

  1. Trigger. Manual dispatch only; the 30-minute schedule is commented out. The admin panel's “Run scraper” button only records a queued run that nothing picks up.
  2. Setup. Check out the repo, set up Node 20, install the whole monorepo and generate the Prisma client.
  3. Fetch. Adapters run one after another. Each makes one request (first page only), with retries and backoff.
  4. Per item. Skip it if its URL (host and path) matches a live deal; drop it if the price is missing, zero or implausible; otherwise create or update a ScrapedDeal in PENDING_REVIEW, keyed on source and external id.
  5. Record. A ScraperRun row stores the found and new counts, or an error.
  6. Review. At /admin/scraper the queue shows pending items newest first, capped at 100. The admin must pick a category, then approves or rejects.
  7. Publish. Approval creates an ACTIVE, verified Deal authored by the admin, writes one price-history point, and posts to Telegram if the discount is at least 20% (or there is no price).
🏷️

No category filter

No source is asked for our categories (only the Myntra feed is on-niche by construction). The raw category is stored but never used; a human picks the category at approval. An estimated 75–90% of items would be off-niche for a beauty-first launch (estimate).

📋

No ranking before review

The queue is newest-first and capped at 100; anything beyond row 100 is invisible. Approved deals start with hot score 0 and a posted time equal to the approval time.

⌛

No expiry

Scraped deals never get an expiry time, so they stay ACTIVE until the community or an admin expires them.

🔇

Silent failures

An adapter that fails to fetch returns an empty list, so the run is recorded as completed with 0 found.

6Ranking & community trust

The Hot feed rewards deals that collect votes quickly and lets them fade with age, so fresh, genuinely good deals rise to the top.

Hot score hotScore = (upvotes − downvotes) / (ageInHours + 2)1.5
Updated on every vote and recomputed for all live deals every hour.
💥

LOOT

Badge at hot score > 5. Separately, users who saved a deal get a “just went LOOT” push when it crosses 2.

🔥

HOT

Badge at hot score > 2.

☀️

WARM

Badge at hot score > 0.5.

✈️

Telegram

Auto-posted to the channel the first time its hot score reaches 10.

“Loot” currently means four different thresholds in different parts of the code (badge, push, Telegram and share card). The homepage Loot section shows deals with hot score above 2 or a discount of 40% or more.

Trust signals on a deal

  • Verified: deals an admin approves from the scraper review queue are marked verified.
  • Honest pricing: the “No fake MRP” badge is withheld when the claimed discount is 80% or more; the deal shows a neutral “price checked” state instead.
  • Price history: price points are recorded, so “all-time low” claims can be checked.
  • Still working?: live WORKING vs EXPIRED counts, plus coupon-worked counts.
  • Reputation: contributors build reputation from votes, comments, approvals and referrals, shown on the leaderboard.

Gap The deal page's structured data for search engines includes a rating derived from the hot score rather than from real reviews, which contradicts the brand promise.

8Background jobs

Eight Vercel cron jobs (configured in apps/web/vercel.json) call HTTP endpoints of the web app, and one GitHub Actions workflow runs the scraper. Schedules are in UTC; India (IST) is UTC+5:30.

JobSchedule (UTC)What it does
expire-dealsevery 15 minMarks every ACTIVE deal whose expiry time has passed as EXPIRED, in one bulk update.
send-alertsevery 30 minMatches ACTIVE deals posted in the last 31 minutes against active alerts; sends Expo pushes in batches of 100 and one email per user.
expiry-alertsevery 30 minFinds saved deals expiring within 2 hours and notifies the savers by push and in-app message, once per deal.
price-watch-checkhourly, :00For each active price watch, looks for a deal at or below the target price; notifies by push, email and in-app, then switches the watch off (one-shot). Runs even though the watchlist page is flagged off.
recalc-hotscoreshourly, :00Recomputes the hot score of every ACTIVE deal so decay applies without new votes; sends “just went LOOT” pushes to savers when a deal crosses 2.
daily-digestdaily 08:00 (13:30 IST)Emails the top deals of the last 24 hours, personalised to each user's daily alerts; also sends the top deal as a web push to all subscribers.
weekly-digestMondays 09:00 (14:30 IST)Emails the week's top 10 deals by hot score to users with active alerts.
sale-event-alertsdaily 08:00 (13:30 IST)Emails users subscribed to a sale event that starts within 24 hours, plus a web push to all subscribers. Runs even though the sale calendar is meant to be hidden.
scraper.yml (GitHub Actions)Paused (was every 30 min)Runs the five scraper adapters into the review queue. Manual dispatch only since 14 June 2026; 10-minute job limit.

Every cron handler reports failures to Sentry. None of them takes a lock or records its last successful run, and several fire at the same minute; see Background jobs topology. Whether the Vercel plan honours the sub-daily schedules could not be confirmed from the code.

Sentry in the web app and the scraper; every cron job reports failures.

Content security policy, HSTS, frame denial, and strict referrer and permissions policies on every response.

13Known limitations

The main gaps today. What to do about each, and in what order, is on the Recommendations page.

  • Supply No automated deal supply: the scraper is paused and has no feed key. Recommendation →
  • Moderation The duplicate check matches a new submission against itself, so ordinary submissions are auto-rejected. Recommendation →
  • Deal page Pending, rejected and FRONTPAGE deals all show as “expired”, and the page's search-engine rating is not based on real reviews. Recommendation →
  • Scraper Silent fetch failures, no category filter, an unsorted queue capped at 100, and scraped deals that never expire. Recommendation →
  • Notifications App push not configured; tapping a push doesn't open the deal; Web Push is broken. Recommendation →
  • Accounts No password reset or email verification; onboarding never appears for signed-in users. Recommendation →
  • Speed Functions run in US East, pages are almost never cached, and the homepage runs 13 queries it never renders (1.7 s time to first byte, measured cold). Recommendation →
  • Jobs Cron jobs have no locks or run history, and overlapping windows can double-send. Recommendation →
  • Flags Four of the eight flags gate nothing, and the other four hide only a page. Recommendation →
  • Delivery No staging, manual production migrations, and no deploy gate on CI. Recommendation →
  • Security Security hardening (tracked privately). Recommendation →
