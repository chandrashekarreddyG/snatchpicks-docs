Architecture

How SnatchPicks is built

One Next.js application on Vercel is both the website and the API. Every client talks to it, one Postgres database is the source of truth, and background work runs on cron. This page shows that shape today, the target it is moving towards, and three lifecycles end to end.

Design decisions worth knowing

  • One backend. The website is the API. The native app and extension are thin clients, and no app-only features ship before product-market fit.
  • JWT sessions plus edge checks. Admin access is checked centrally in middleware from the signed token, and again in each admin route (a CI script enforces it).
  • Scraped deals never go live automatically. They land in a review queue, where a human picks the category and approves.
  • Data-driven SEO only. SEO comes from real deal, store, category and intent pages generated from the database; templated buying guides are banned.
  • No microservices. The architecture review concluded the shape is right for this stage; what limits scale is what happens inside the app (Layers).

Anatomy of a request today

  1. Edge. The request reaches Vercel, whose functions run in US East today. Nothing is served from the CDN cache: the homepage, for example, is returned as non-cacheable.
  2. Middleware. Admin paths need an admin role in the signed session token; write endpoints are rate-limited per IP through Redis; an app Bearer token becomes the session cookie.
  3. Page or route handler. Reads the session, applies a guard for user and admin actions, validates the body where a schema exists, and queries Prisma directly. Most pages render the shared header, which reads the session on every render.
  4. Side effects. Telegram posts, in-app notifications, AI summaries and reputation updates run inside the handler, some without being awaited.
  5. Response. Routes return database rows as they are, with no versioned contract, so clients code against the table shape.

3Layers: today vs target

Today the business logic lives in route handlers and pages, which talk to the database directly. The target, from the November 2026 architecture review, keeps one Next.js app but adds a shared rules package, a server layer that owns all data access, a handler kit, a versioned API, an outbox and a job runner.

9Background jobs topology

Eight Vercel cron jobs call HTTP endpoints in the web app; the scraper runs as a separate GitHub Actions workflow. Schedules are UTC.

When jobs collide

Moment (UTC)Jobs starting at once
Every hour at :005: expire-deals, send-alerts, expiry-alerts, price-watch-check, recalc-hotscores
Daily at 08:007: the five above plus daily-digest and sale-event-alerts
Mondays at 09:006: the five above plus weekly-digest
Every hour at :303: expire-deals, send-alerts, expiry-alerts
:15 and :451: expire-deals

Current issues Gap

  • No locks and no last-run state, so a slow run can overlap the next one.
  • send-alerts looks back 31 minutes on a 30-minute schedule, and its daily and weekly pass runs twice in the 02:00 hour, so alerts can be sent twice.
  • price-watch-check sends everything at once, with no bound on concurrency.
  • No time limits set on cron routes.
  • Digests send web push by calling the app's own endpoint over public HTTP.
  • Four copies of the Expo push sender.
  • Jobs keep running for features whose flags are off.

Target Target

  • Job runner: a Postgres advisory lock per job, a run-history table (last success, cursor, counts), paging with bounded concurrency, a time limit per route, and direct service calls instead of HTTP self-calls.
  • Outbox: services write domain events (deal_approved, deal_promoted, price_dropped, deal_expiring) in the same transaction; a drain job, later a queue, runs the handlers.
  • Exactly-once alerts: one delivery row per alert and deal, unique on the pair.
  • One sender per channel (Expo, Web Push, Telegram, email, in-app).
  • Scraper: per-source runs with a lock and a cursor, moved next to the database in India.
