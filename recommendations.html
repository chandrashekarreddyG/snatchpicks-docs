Enhancements & recommendations

Fix the loop, then scale it

The SnatchPicks loop works on paper: deals come in, get checked, get ranked by the community and get pushed to alerts. In practice, deal supply is close to zero, a bug rejects normal user submissions as duplicates of themselves, and caching, server location and the lack of a domain layer limit scale. The fixes are incremental: small, independent PRs inside the existing Next.js app. There is no rewrite.

Proposed · pending owner sign-off One Next.js app · no rewrite Small, independent PRs

1Summary

The five findings that matter most. Each is expanded in the sections below.

🛒

No real deal supply yet

The scraper schedule is paused and no feed credentials are configured, so the feed is almost empty.

🔁

Submissions reject themselves

Every normal user submission matches its own pending row as a duplicate, so it is auto-rejected.

🌏

Far from users, no caching

Functions run in US East while users are in India (about 200 ms+ per request, estimate). Pages are not cached; the homepage took 1.7 s to first byte cold.

🧱

No domain layer or API contract

121 files import the database client directly, and API routes return raw database rows.

🔔

Notifications aren't reliable

Side effects run inline with no outbox, so alerts can be lost or doubled. Web Push is broken and capped at 500 subscribers.

3v0 launch plan

Goal: ship the smallest loop that proves demand, then iterate. Launch is not blocked on a large feature set.

Principles

  1. Ship one loop. Deals come in, get verified, get seen, get clicked out. Everything else waits until a metric asks for it.
  2. Hide, don't delete. Feature flags hide surfaces for v0. The code stays and returns when the data justifies it.
  3. Hill-climb one bottleneck at a time. Each release targets the currently worst metric. Releases are gated on metrics, not dates.
  4. Small, safe changes. One issue and one PR per change, CI green before merge, changelog and docs updated in the same PR.

5v1 release plan

v1 takes SnatchPicks from "a loop that works" to "a product that holds up at 10k–100k daily users and runs without daily founder curation". It starts only after v0 through v0.4 have shipped and met their gates.

What v1 is

  1. The community runs the feed. Most deals and votes come from users. Quality tiers (New → Popular → Frontpage) replace founder curation.
  2. Notifications are the product. Alerts fire on quality (for example, "tell me when it's Popular"), on the channel the user picks, exactly once.
  3. It scales without a rewrite. The monolith stays. Fan-out, counters and caching move to patterns that hold to 100k daily users.
  4. A second vertical. Fashion is fully live on top of beauty.
  5. All surfaces are generally available: web/PWA, native app (Play Store and App Store), Chrome extension and social channels.

8Scraper and deal-supply improvements

The scraper is the main source of supply, and today it delivers almost nothing. The analysis covers how it runs, what it measures and what to fix first.

Today

  • Probably no deal has ever reached production. The workflow ran 50 times in June 2026: 48 failed and 2 succeeded, and the scraper step took 1–6 seconds. No feed credentials are configured, so every adapter skips. The schedule has been commented out since mid-June 2026.
  • No category or niche filter. Sources return all categories, and a person picks the category at approval. An estimated 75–90% of queued items would be off-niche for the beauty-first launch (estimate).
  • No ranking before review. The admin queue is newest-first and capped at 100 rows. Approved deals start at hot score 0.
  • Fetch failures are reported as success. Each adapter returns an empty list on error, so a run is recorded as completed with 0 found, and nothing reaches error monitoring.
  • Several defects would break or degrade it once feeds are connected: approval probably fails when no store is picked (estimate); affiliate redirect links break deduplication; scraped deals never expire.

Pipeline

Stages

StageWhat it does
SchedulePer-source cadence: Amazon price drops every 10–15 min, affiliate offers every 15 min, aggregator feeds every 15–30 min, catalogue feed hourly. A per-source lock stops runs from overlapping
FetchSources run in parallel within a time budget. Paginate, keep a per-source cursor for incremental runs, cap retry waits at 30 s, use a circuit breaker. Adapters return errors, never a bare empty list
NormalizeUnwrap the aggregator redirect, strip tracking parameters, lowercase the host. Product key = store plus store product id, otherwise a hash of the canonical URL. A content hash skips unchanged items
EnrichStore resolved from the host. Category from a mapping table (seeded for beauty, fashion, baby), with keyword fallback. Prefer the product image over the merchant logo. 30-day low from our own price history
Quality gatesPrice present and sane; real MRP only; the core fake-MRP rule; niche gate; duplicate check across all sources; minimum discount. Each failure records a reason
Score0–100 weighted score, stored with its breakdown so an editor can see why an item ranked high
RoutePublish, review queue, or reject, by score band
PublishApprove through the lifecycle in one transaction: create the deal with canonical key, affiliate URL, expiry and first-seen time; write price history; seed a small hot score; emit a publish event
NotifyThe outbox drain matches instant alerts, posts top-scored deals to Telegram, and creates in-app notifications. Idempotent per alert and deal
Refresh and expiryUpdate last-seen times and live prices. Expire on the source end date, after 3 missed runs, on a price rise above the published price, or after a 72 h TTL
WritesPer source per run: one select, one batch insert, one batch update, one run record. About 10–20 queries instead of about 835

While auto-publish is on hold Phase C deals that would qualify go to the top of the queue with an editor push notification. The realistic target is then live at ≈ 09:15–09:40 during staffed hours (estimate).

Phase C timeline

  1. 09:00:00: the deal starts on Amazon.
  2. 09:00–09:10, detected: by the first of several paths: a tracked-product poll (hot tier every 10 min), an Amazon category search with a minimum saving percentage (every 10 min), the Keepa deals poll (every 10–15 min; Keepa's own detection lag varies, estimate), or a community post at any time.
  3. +≤ 5 s, normalize: the ASIN becomes the product key; dedup across all paths; enrich (store = Amazon; category via browse node → mapping).
  4. +≈ 1 s, verify: one Creators API lookup (up to 10 ASINs per call) returns the current price, the saving basis (list price, so no guessing), the saving percentage, deal details (start and end times, percent claimed, lightning or Prime-exclusive), availability and the affiliate detail URL.
  5. +< 1 s, gates and score: fake-MRP rule against the real list price, niche, minimum discount, in stock; then score.
  6. +< 1 s, publish: through the lifecycle. Expiry = the API's deal end time; badges ("Lightning deal", "38% claimed"); price history row; outbox event.
  7. +≤ 1 min, notify: outbox drain → alert matching → push and Telegram.
  8. Every 10 min, re-verify: the hot-tier poll updates "percent claimed" and expires the deal on sell-out, price reversion or end time.
  9. 15:00: automatic expiry.

India-specific opportunities

🏦

Bank-offer stacking

Bank-offer pages exist behind a flag. Show stacked offers (coupon, bank offer and cashback) on the deal card once the bank-offer flag is decided. This is where Indian shoppers save most.

The sale-event calendar is hidden today. Replace it with curated calendar data for major Indian sale days. Feed it into alerts and into event pages for search.

WhatsApp sharing
