How the scraper works

Where SnatchPicks gets deals from partners, how each one is checked, and why a person approves every deal before anyone sees it.

🔌 Partner APIs and feeds only 🧪 Duplicate and price checks 🧑‍⚖️ Human review 🕒 Every 30 minutes, when switched on

1What the scraper does

The scraper is one script that collects deals from SnatchPicks' partners: a price-tracking service for Amazon and affiliate programmes for Flipkart, Myntra and two affiliate networks, Cuelinks and INRDeals. It asks each partner for its current offers, turns every offer into the same simple format, throws away duplicates and items with impossible prices, and puts the rest in a review queue. A person then picks a category and approves or rejects each one; approved deals go live on the site and the app, and can be shared on Telegram and in deal alerts. Despite the name, it doesn't scrape retailer websites; it only reads data that partners provide for this purpose.

Prefer a picture? The 3D architecture page shows the same pipeline as a model you can rotate, with deals flowing through it.

3The journey of one deal

Follow a single offer, say a moisturiser at 35% off, from a partner feed to a shopper's phone.

  1. A run starts. A schedule can start the scraper every 30 minutes, or a team member starts it by hand, for every source or just one.
  2. The partners are asked in turn. Amazon (through Keepa), Flipkart, Myntra, Cuelinks and INRDeals. A source whose partner key isn't set up is skipped.
  3. The offer is fetched and tidied. Each request has a time limit and is retried a few times if the partner is briefly unavailable. The offer is then put into a common format: the partner's own ID, title, link, price, original price (MRP), image and category.
  4. Three checks run, in order. Is it already on the site (by link)? Does the price make sense? If both pass, it is saved to the review queue as “pending review”, or, if the partner sent it before, its price is refreshed.
  5. The run is recorded. Each source gets a run record: when it ran, whether it finished, how many deals it found and how many were new.
  6. A person reviews it. An admin picks the category, can tidy the title or add a coupon, and approves it. The deal goes live, marked as verified, and, because it is at least 20% off, it can be posted to the Telegram channel.
  7. Interested shoppers hear about it. Every 30 minutes, the deal-alert job picks up newly approved deals and notifies people whose alerts match, by email or app push: straight away, or in their daily or weekly digest.

4The checks

SnatchPicks promises “No fake MRP. Ever.” The checks keep obvious junk out; a person handles the rest.

CheckWhat it looks atWhat happens
DuplicatesThe offer's link, compared with every deal already live or waiting for moderation. Only the store address and product path count; tracking tags are ignored.A match is skipped, so the same product isn't listed twice.
Price sanityA price of zero or less, or above ₹1 crore, is treated as bad data. An MRP that isn't above the price is a fake discount.A bad price drops the item. A bad MRP is removed, but the item stays. Offers with no price at all, such as coupons, pass.
Review queueEach item is stored once per partner and the partner's own ID.New items wait as “pending review”. An item seen again only gets its price refreshed; a reviewed item keeps its decision.

Why a person reviews every deal

  • Trust is the product. One fake “was ₹9,999, now ₹999” listing undoes a lot of goodwill; automatic checks only catch the obvious cases.
  • Partners send everything. Feeds cover every category, and SnatchPicks is launching with beauty and skincare, so someone has to pick the right category and leave out what doesn't fit.
  • Partner data can be wrong. Titles, prices and images are sometimes stale or garbled. A reviewer can fix the title or add a coupon or bank offer before approving.
  • Nothing goes out unseen. An approved deal can be posted to Telegram straight away, so a person should see it first.

Later, a score could sort the queue so the best deals are reviewed first, and eventually let high-scoring deals from trusted stores skip the wait (see What's changing).

5Schedule and runs

How often

The scraper is designed to run every 30 minutes. That schedule is switched off for now: no partner is connected yet, so scheduled runs would only find nothing. Until then the team can start a run by hand at any time, for all sources or just one. Each run has a ten-minute limit.

What a run record holds

FieldMeaning
SourceWhich partner this record is for. Every source gets its own record in each run.
StatusRunning, completed or failed.
Deals foundHow many offers the partner returned.
New dealsHow many of them were added to the review queue for the first time.
Started and endedWhen the source's part of the run began and finished.
ErrorA short reason, when the run failed.

When a partner is down

Each request waits a limited time. If a partner is busy or briefly unavailable, the scraper waits and tries again a few times, waiting a little longer each time, then moves on to the next source, so one partner's problem doesn't block the others.

Today, outages are not yet surfaced clearly. A partner that is down can look like a quiet run with no new deals. Recording these as failed runs is in progress.

6What's changing

These improvements are being built and reviewed. None of them has shipped yet.

  • In progress Cuelinks Offers API v3, with pagination. Cuelinks has retired the API version used today. The new version is read page by page, with a short pause between pages and a limit on how many pages are read, and each offer keeps its categories.
  • In progress Failed fetches recorded as failed runs. When a partner is down, the run record will say “failed” with a short reason. A source that isn't set up will show as skipped, and the whole job fails if every connected source fails.
  • In progress Duplicates found by the real merchant link. Affiliate networks wrap product links in their own redirect links, which can look alike for different products. The duplicate check will compare the store link inside the redirect instead; the redirect link is kept so clicks are still credited.
  • In progress Invalid prices dropped. Placeholder prices that some feeds send, such as -1 or “N/A”, will be rejected by the price check instead of being saved as “no price”.
  • In progress Safer logging. Run logs will keep only what is needed to understand a run.

Further out Target

The target pipeline adds a niche filter that sets aside off-category items before review, a score that sorts the queue, and expiry, so a deal leaves the feed when the partner's offer ends (saving Cuelinks offer end dates is part of the work in progress). The target ingestion pipeline has the details and the order of work.

7Rules we follow

  • Partner APIs and feeds only. Every source is an official API or an affiliate feed that the partner offers for this use.
  • No scraping of retailer websites. The scraper never reads store pages; where there is no partner access, there is no source.
  • Respect partner terms. Follow each programme's terms on how often to ask, how to show prices and links, and how to credit clicks.
  • No made-up data. A source without access returns nothing rather than placeholder deals.
  • A person approves before anything goes live. Feed items wait in the review queue until an admin accepts them.
